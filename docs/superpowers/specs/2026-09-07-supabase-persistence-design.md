# Supabase persistence design

**Date:** 2026-09-07
**Status:** Accepted

Replaces local SwiftData persistence with Supabase as the source of truth for the
Work log, via a second implementation of the existing `EntryService` protocol.

## Context

Chronik stored Entries locally with SwiftData, confined to `EntryServiceImpl`
behind the `EntryService` protocol. Moving persistence to Supabase should
therefore be a matter of adding an implementation — but it drags in decisions the
local implementation never had to make: authentication, network failure as a
routine case, an explicit wire schema, and a toolchain floor.

## Decisions

### D1 — Remote-only, not offline-first

`SupabaseEntryService` becomes the sole registered `EntryService`. There is no
local cache and no sync engine.

`EntryServiceImpl` (SwiftData) and its tests stay in the tree, unregistered. An
offline-first design needs `updatedAt`, delete tombstones, conflict resolution
and a sync engine — a project far larger than swapping an implementation. Keeping
the local implementation alive means that project starts from working code rather
than from a rewrite.

**Consequence:** the Work log is unreadable and unwritable without network.
This is a real cost for a work log, which is exactly the kind of thing one jots
down on a train. Revisit if it bites.

### D2 — Anonymous sign-in with RLS

The Supabase anon key ships inside the app binary and is extractable. Without an
authenticated user and row-level security, `entries` would be a world-readable,
world-writable table.

`signInAnonymously()` (enabled in the Supabase dashboard) gives a real
`auth.uid()` to key RLS on, with no login UI. Supabase supports linking an
anonymous user to a real identity later, so Sign in with Apple remains available
without a data migration.

**Consequence:** identity is per-install. A lost device is a lost Work log until
the anonymous identity is linked to a durable account.

### D3 — `SupabaseCore` package owns the client and session

The `SupabaseClient` and auth session are process-wide concerns, not feature
concerns; a second feature package must not build a second client and a second
session. `SupabaseCore` owns them. `SupabaseEntryService` lives in the Entries
package alongside the protocol it implements.

`EntryService` stays internal to `Entries` — no visibility changes anywhere.

### D4 — `EntryService` is no longer `@MainActor`

It was `@MainActor` because SwiftData `ModelContext` work was synchronous and
main-bound. Under Supabase the bodies are network I/O, and `@MainActor` would put
request building, JSON decoding and row mapping on the main thread.

The protocol becomes `Sendable` with async requirements. View models stay
`@MainActor` and simply `await`.

### D5 — Configuration from a gitignored xcconfig

`SUPABASE_URL` and `SUPABASE_ANON_KEY` come from
`Chronik/Config/Supabase.local.xcconfig`, which is gitignored. The tracked
`Chronik/Config/Supabase.xcconfig` declares both as blank and pulls the local file
in with an optional `#include?`, so a fresh clone builds without it and traps at
launch instead of failing to configure.

This replaces an earlier build-time-environment approach. Environment variables
worked under `xcodebuild` but not for Xcode.app launched from the Dock, which does
not inherit the shell — the documented "open the project and run" workflow would
have produced an app that builds and dies at launch. An xcconfig has no such
asymmetry.

**xcconfig truncates URLs.** `//` starts a comment, so
`SUPABASE_URL = https://project.supabase.co` is stored as `https:` — verified, not
theoretical. The documented form omits the scheme
(`SUPABASE_URL = project.supabase.co`) and `SupabaseConfiguration` supplies
`https://`; a full URL needs `$()` escaping (`http:/$()/localhost:54321`). A value
ending in `:` is treated as this truncation and trapped by name, because it would
otherwise pass every check and yield a URL pointing nowhere.

The values are carried into the app by a real Info.plist template
(`Chronik/Info.plist`, generated by xcodegen from the target's `info.properties`)
rather than by `INFOPLIST_KEY_SupabaseURL` build settings. `INFOPLIST_KEY_<name>` only supports
Xcode's documented key allowlist: custom keys expand correctly as build settings
and are then **silently dropped** from the generated plist, producing a build that
succeeds and an app that traps at launch. `GENERATE_INFOPLIST_FILE` stays on and
merges its keys into the template.

Xcode.app launched from the Dock does **not** inherit the shell environment, and
would otherwise construct a client against empty strings that fails at runtime
with an opaque error. `SupabaseCore` therefore reads the values once and traps
with an explicit message naming the missing key.

`project.yml` also gains a shared `Chronik` scheme. Schemes were previously
autocreated into `xcuserdata` and wiped by every `xcodegen generate`, which broke
`xcodebuild -scheme Chronik`.

Note the anon key is designed to be publishable; gitignoring it is tidiness, not
security. D2's RLS is what actually protects the data.

### D6 — Schema

```sql
id         uuid primary key
user_id    uuid not null default auth.uid()
day        date not null
created_at timestamptz not null
title      text not null
duration   numeric(5,2)
notes      text
```

`day` is `date`, not `timestamptz`. CONTEXT.md is explicit that "Entries belong to
a Day, never to a moment". With `timestamptz` a Prague entry would store as
`22:00Z the previous day` — correct on round-trip in the same timezone, wrong the
moment the user travels or inspects the table by hand. Mapped `"yyyy-MM-dd"` to
and from `Calendar.current.startOfDay`.

`duration` is `numeric(5,2)`, preserving the existing `Decimal?` behavior. Storing
minutes as `integer` would sidestep a Foundation `Decimal`-via-`Double` decoding
quirk, but rounds on write (`1.33h -> 80min -> 1.333h`), a user-visible change.
At hour granularity the quirk is not reachable.

`created_at` is client-sent rather than `default now()`, because
`EntryFormViewModelImpl` preserves the original `createdAt` when editing and a
server default would clobber it.

### D7 — `user_id` never reaches the domain model

It lives only in the internal row DTO. The user is ambient — it is the session,
not a property of a work-log entry — and putting it on `Entry` would ripple into
both view models, both test targets and the retained SwiftData implementation for
no benefit.

The column defaults from `auth.uid()`, so the client cannot write a row
attributed to someone else. The insert policy is a formality rather than the only
thing preventing a spoofed `user_id`.

### D8 — Lazy session, not eager sign-in

`SupabaseCore` exposes a single entry point that performs `ensureSession()`
internally before handing back a client. There is no way to obtain a client
without a session, so sign-in ordering bugs are structurally impossible.

Signing in eagerly at launch would put a network call on the launch path, where a
cold start with no signal either blocks the first frame or races the first
`fetchAll()`. Lazily, a failed sign-in surfaces through the path the UI already
handles — `LoadableCollectionView` renders it with a working retry button.

### D9 — Domain error type

`EntryServiceError` (`offline`, `notAuthenticated`, `notFound`, `server`)
conforming to `LocalizedError`.

Both view models already display `error.localizedDescription`. Under SwiftData
that error essentially never fired; under Supabase offline is the common case, and
a raw `URLError` renders as "The operation couldn't be completed."

### D10 — Read path

Ordering is server-side (`day` desc, `created_at` desc) even though
`EntriesViewModelImpl.group` re-sorts — it costs nothing and is a precondition for
pagination.

`fetchAll()` carries `.limit(500)`. Pagination is deferred; the limit makes the
failure mode "oldest entries missing" rather than an unbounded payload that grows
forever on every screen appearance.

`delete` keeps its delete-then-refetch round trip. One extra request buys a view
that cannot drift from the server; optimistic local removal is a correctness
problem not worth taking on at ~200ms.

`update` uses `.select()` and throws `.notFound` on zero matched rows, preserving
the SwiftData implementation's throw-if-missing behavior. PostgREST would
otherwise succeed silently.

### D11 — Toolchain floor moves

`supabase-swift from: "2.55.0"`, importing only the `Supabase` product —
`PostgrestMacros` is deliberately not re-exported by the library, so skipping it
keeps swift-syntax and macro compilation out of the build entirely.

supabase-swift 2.50.0 and later require `swift-tools-version:6.1`. Our packages
remain at tools-5.9, which is fine — a 5.9 manifest may depend on a 6.1 one; the
constraint is on the toolchain. But `project.yml` declared `xcodeVersion: "15.0"`
and CLAUDE.md said "Xcode 15+", and **no** usable supabase-swift release builds
under Xcode 15.0 (even the tools-5.10 line needs 15.3+). That declaration was
already fiction relative to the development machine and is corrected here rather
than left to fail with an unexplained manifest parse error.

`xcodeVersion` moves to `16.3`, the first release shipping a Swift 6.1 toolchain.
`SWIFT_VERSION` **stays at 5.9**: it selects the language mode for this project's
own sources, and 5.9 remains valid under a Swift 6.3 toolchain. Raising it would
switch on strict concurrency checking, which is a separate piece of work with its
own diff — not a consequence of changing where Entries are stored.

### D12 — Testing

The row DTO's mapping to and from `Entry` is extracted as a pure type and tested:
the `"yyyy-MM-dd"` boundary, `numeric`-to-`Decimal` round-trip, nil `notes`. The
thin PostgREST calls are not tested.

Integration tests against a live project would put network and secrets into
`xcodebuild test -scheme Entries`, breaking the documented test command. Wrapping
the transport in another protocol would add a layer whose only consumer is a test.
The mapping is where the bugs actually live.

The DTO is named `SupabaseEntryRow`; `EntryRow` is already taken by a public
presentation type in the same module.

## Known limitations

- No offline access at all (D1).
- No pagination beyond 500 entries (D10).
- A lost device is a lost Work log until the anonymous identity is linked (D2).
- Credentials must be created by hand on each clone; the URL cannot be written in
  its natural `https://…` form (D5).
